### A named query in a flow

`record.query` with `with: { query: <table>.<key> }` (`book.myShelf`) reads a declared query; it takes no clauses beside it. The step reads the flow's inputs named like the query's params, and its own paging inputs, named after the step's key: for the step `read`, `readAfter` (or `readBefore`) and `readLimit` (1 to `pageSize.max`); for `readShelf`, `readShelfAfter` and so on. So two such steps in one flow page independently, each by its own cursor. The flow declares an optional input of each of those names it exposes; the step runs even when every one of them is absent. A query's params come only from the flow's inputs: a param named like a step's key is refused at the save (`QUERY_PARAM_FROM_ACTION`; filter by a computed value with an inline `record.query`), and so is a param with no `default` that is not `optional` when the flow has no input of its name (`QUERY_PARAM_NO_INPUT`). The inputs named like the query's params count as read: removing one, or renaming it, is refused while the query reads it (`REMOVED_STILL_USED`). A paging input is optional: removing it only warns, and the step then pages by the query's `pageSize.default`. A step key named like a paging input (`shelfLimit` for the step `shelf`) is refused the same way. An `optional` param that no input of the flow feeds is saved with a warning (`QUERY_PARAM_OPTIONAL_NO_INPUT`): the read never narrows by it. Rename a param in the query and the flow's input together. The step's value is `{ records, nextCursor?, prevCursor? }`, or `{ record? }` for a `one` query; type the flow output that carries the whole page `object`, and one that carries only `read.records` a list (`object[]`). It is billed as one step. Read the page in a later step as you would any `record.query` page (`read.records`) — a flow that computes over the page is still a flow; it is just not a query endpoint (below).

**Who it reads as.** A `scope: "caller"` query reaching a person-owned table needs a signed-in person. The plan refuses `QUERY_CALLER_WITHOUT_PERSON`, naming the start, the flow, the query and the table, when a flow that reads such a query — directly, through `flow.invoke`, or inside an `if` branch — can start with no person: a schedule, a trigger, processing of a project-owned table, an eval suite with no run-as member. Processing of a person-owned table (it runs as the record's owner), `flow.start-per-person` and a credentialed endpoint called with a session start with one. An `auth: "none"` endpoint over such a flow is refused `PUBLIC_ENDPOINT_NEEDS_USER`, naming `record.query`; serve the public part from a `scope: "project"` query. An API key calling a credentialed endpoint over it gets `403` before any read, as for any per-user read ([endpoint-answers.md](endpoint-answers.md), §8).

### A query endpoint: declare the path, nothing else

A `GET` endpoint naming a `flow` (not `async`) whose answer — `responseBody`, or the flow's only output — is a named query's page returned unchanged is a **query endpoint**. Its contract comes from the query as it is now; nothing of the query is stored on the endpoint:

- **Declare no query-string params and no `inputs`.** The request's query string takes the query's params, typed and bounded as declared, plus `after`, `before` and `limit`. A param binds the flow input of the same name; `after`, `before` and `limit` bind the answering step's own paging inputs (`readAfter`, `readBefore`, `readLimit` for the step `read`). A path parameter (`{id}` above) is declared as today and feeds the param of its name. A flow input typed otherwise than the query gives it is refused `QUERY_INPUT_TYPE`.
- **Never declare `after`, `before` or `limit` in the contract.** An endpoint that does — or an `async: true` one — is not a query endpoint: it keeps the contract it declares, and the plan warns `QUERY_ENDPOINT_NOT_DERIVED` naming why.
- **The answer** is `{ items, nextCursor, prevCursor, paging: null }`, cursors `string | null`: walk forward with `?after=<nextCursor>` and back with `?before=<prevCursor>`. A query ranked by meaning takes no cursor and answers both `null`. A `one` query answers the record itself, and the same `404 NOT_FOUND` for a record that does not exist and one the caller may not read.
- **Refusals**: an unknown query-string key, a value of the wrong type, out of bounds or missing, `?limit=` past `pageSize.max` — `422 VALIDATION_FAILED` naming it. A cursor from another query, another person or other params — `400 QUERY_CURSOR_INVALID`, never another read's rows.
- **A query, selection, table, type, relation or step edit** reaches the endpoint's next request with no endpoint save, and is judged for its callers: the plan's (or the write's) `contractChanges` lists the endpoint with each change. Adding a field or a param, or widening a bound, is `safe`. Removing a field the items answer, narrowing `limit` or retyping a param is `breaking`, and pointing the step at another query usually is (the check compares what callers meet). A breaking write is refused `409 CONTRACT_BREAK_NOT_ACCEPTED` until `acceptBreaks: {endpoints: [<key>]}` names it, sent by an admin of the project; removing a relation's pair takes no `acceptBreaks` and is made in the project document instead. The endpoint itself is not written and its `version` does not move.
- **An endpoint whose flow edits the page** (a transform counting or reshaping it) is an ordinary endpoint and answers exactly what its flow outputs.

**ETag.** A query endpoint whose flow is exactly one enabled named `record.query` step and its `return`, every input from the request, over a query that reads only fields and links — no `term`, `stream` or `semantic` clause anywhere in it, its sets, base or linked reads, no vocabularies, no file field — answers an `ETag`. Send it back as `If-None-Match`: while nothing the answer depends on changed (the records and links of every table the query reads, the project's configuration, the caller, the params, the page), the answer is `304` with no body, no run and no charge. Add a guard or any other step and the endpoint still pages by the query but answers no ETag. Every query-endpoint answer carries `Vary: Authorization, Cookie, Accept` (`Accept: text/event-stream` asks for a live stream instead); a `200` or a `304` also carries `Cache-Control: private, no-cache` and the `ETag`; a refusal carries neither. The project's OpenAPI document says which operations answer `304`.

### Try a query before a flow uses it

`POST /v1/tables/{id}/queries/{key}/preview?project=<projectId>` (`{id}` the table's key or id, `{key}` the query's) with `{ "asUserId": <a member>, "params": { "genre": "poetry" }, "limit": 5 }` reads an applied query as that member — `asUserId` is left out for a query reaching no person's records — and answers the page (`items`, `nextCursor`, `prevCursor`, `paging: null`) beside `itemSchema` (one row's JSON Schema), `tables` (every table the read reaches: `book`, `follow`, `hide` for `myShelf`) and `clauses` (what it ran, base and params merged in). It needs the viewer role and writes, charges and runs nothing. An unknown key is `404`; a caller query with no `asUserId`, `422`. It reads applied queries: plan and apply the query first.

### What a query cannot say yet

Write these as a flow step after the named read (the endpoint then answers what the flow computes, with no derived paging), or inline:

- **OR across clauses** — a query's clauses are all required; "followed authors' books, or anything tagged featured" is two reads.
- **Order by a linked record's value** ("collections by their newest item") — keep that value on the record ([records-and-endpoints.md](records-and-endpoints.md), §10) and order by it.
- **A set over `link` or `term` clauses** — a set holds `field` clauses and sets only.
- **A value the run computes** — a query reads no flow value; a filter built by an earlier step is an inline `record.query` ([record-query.md](record-query.md), §9).
- **Computed answer properties** — a selection renames, maps an enum's values, gives a default and links; a `value.transform` after the read computes.
- **A contract that pages by another name** (`?cursor=`) or a page of a read with clauses written in place — return the `record.query` page from the flow and declare `answer: { select: <table>.<selection>, list: true }` on the endpoint: it answers `{ items, nextCursor }` in the selection with no expression step ([endpoint-answers.md](endpoint-answers.md), §8).
