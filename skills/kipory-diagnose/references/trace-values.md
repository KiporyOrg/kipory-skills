# A trace's values, and when there is none

Read this when you need the values a run's steps gave: how to read a trace in order, and how to get the values when no trace was kept.

## Reading a trace

1. **Start from `output`.** If it is missing an output the caller declared, you have your failure — also the usual cause of a 502 through an endpoint.
2. **Then `stepOutputs.writes`.** One entry per value a step gave, named by `flowId` and `stepKey` (with its `branchId` inside an `each`), so a sub-flow's steps and each element's run are told apart. A value that is present and empty (`[]`, `""`) is the real "ran and gave an empty answer" signal. A step with no entry gave nothing: read its timeline row for why — it failed, its branch did not run, or it was never reached. `null` on `stepOutputs` means the run recorded no steps, not that there were none.
3. **A failed step's entry carries its `error`** beside its key, so a trace alone tells you which step stopped and with what.
4. **Compare a good run to a bad one.** The fastest way to find a step whose behaviour changed. The trace listing is cursor-paged, newest first: `nextCursor` set means older traces exist, so pass `after=<nextCursor>` (`limit` is 100 at most per page) or narrow with `recordId`. Each trace names its `runId`, so a trace and the run's timeline join directly.
5. **Check `durationMs`** if the complaint is slowness — null means the writer did not time itself, not that the run was instant. Each step's own `durationMs` is on its row in `GET /v1/runs/{runId}/timeline`, and a run that started late carries `queued` on `GET /v1/runs/{runId}`: how long it waited before starting, and what held it.

Values are truncated at write time — embeddings reduced to their head, long lists capped, anything over the row budget replaced by a `dropped-oversized` note naming the size. You are reading evidence, not a replay.

## When there is no trace to read

- **A record's processing run that was not sampled:** replay it on the same record without writing — `POST /v1/flows/{id}/preview/stream` with `{ "input": { "kind": "record", "recordId": "<id>" }, "apply": false }`. Each `step-ended` frame carries `slotBag`, that step's value under its key, and `runState`, the run's shared state at that point. It bills like any preview.
- **Any run you can reproduce:** queue a preview of the same inputs — `POST /v1/flows/{id}/preview-runs` with `{ "input": { "kind": "slots", "inputs": { … } }, "apply": false }`, where `inputs` is the bad run's inputs keyed by the flow's input names (a trace's `inputs`, when one was kept) — and read the new run's `/trace`, `/timeline` and `/spend`. A queued preview of the project's own flow writes its trace as it runs (a platform flow's writes none), and with `apply: false` nothing it stages is applied.
- **The next runs, recorded whole:** `PATCH /v1/flows/{id}/value-recording` with `{ "until": "<ISO time>" }` makes every run this flow starts keep its trace until then, whatever the sampling; `until` may be at most as far ahead as traces are kept (`kept-for.trace-days`, 7 days by default). A run of it called from another flow (`flow.invoke`) keeps its trace only when its caller's run does, and a project whose trace rate staff set to 0 keeps none. `{ "until": null }` stops, and `GET /v1/flows/{id}/value-recording` says whether it is on. It changes what runs keep, never what they do (EDITOR).
- **A failed record run:** `failedInputs` on `GET /v1/runs/{runId}` is what each failed step was handed when it failed, by `stepKey`, each input by its name, for a run's first 20 failures. Long values are cut, and a field whose name contains key, token, secret, auth, password, credential, cookie, bearer, jwt, session or signature reads `[redacted]` at any depth, whatever it holds (a `keywords` field too). It is empty for any run that did not process a record (a request, endpoint, schedule, trigger or preview run), for a step that failed before its function was called, and for a failure of the whole run (a timeout, a refusal at commit). They are recorded values, under the same two rules as a trace: none are kept while the project's recording of record runs is turned off (whatever a flow's "record every run" says), and they are cleared once the run is older than recorded values are kept (7 days by default) — `failedInputs` then reads empty, though the run and its failure stay.
- **A refused synchronous call:** the run's id is the response's `x-request-id`. Its timeline names the step and why, and `GET /v1/runs/{runId}/flow-snapshots` the flow as it ran, even when no trace was kept.
- **To practise on a failure:** set `timeoutMs` to `1` on a fetch or model step of a copy of the flow and queue a preview (`POST /v1/flows/{id}/preview-runs`, `apply: false`): the step fails on its time limit and the run is there to read. An inline preview leaves no run, and a 1 ms limit never fires on a step that computes in-process, such as `text.interpolate`.
