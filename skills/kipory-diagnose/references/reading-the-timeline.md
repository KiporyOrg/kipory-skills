# Reading a run's timeline

What each part of a run's timeline tells you, and what to do about it. `SKILL.md` lists these by their first line, under "The sequence".

- **Which action a row is about.** Each row names its action in `actionName` (the name as it was when the run happened) and `actionId`; both are null on the run's own rows (`run-started`, `run-finished`). `flowId` tells a sub-flow's actions from the parent's, and `branchId` a fan-out branch. `GET /v1/runs/{runId}/spend` keys its `byAction` entries by the same `actionName` and `actionId`, so the two reads join on them.
- **Why an action failed.** Its `action-failed` row says so under `detail`: `detail.phase` (`function-error`, `condition-error`, `fanout-error`, `sub-flow-failed`, `platform-fault`, `target-unreachable` for an address whose name did not resolve — the site is gone, nothing was blocked — `ssrf-blocked` for an address the platform refuses, …) and `detail.message`, the action's error text cut to 500 characters (an ellipsis marks the cut; an action that failed the same way earlier in the run carries `detail.messageRepeated: true` instead), beside `detail.tries` (only when the action's job was tried more than once) and `detail.cacheHit` / `detail.rateLimitWaitMs` when they apply.
- **`platform-fault` is not yours to fix.** An action that failed with `detail.phase: "platform-fault"` ran on one of the platform's own accounts — a vendor refused the platform's key or its account is out of credit, or a model provider's account is exhausted — and `detail.message` ends "This is a platform fault, not a fault in the flow" (a model call reads `… provider account exhausted (quota/billing)`). The action is not charged, the deployment's operator is alerted by the same failure, and the same run succeeds once the account is topped up. An unattended run that failed this way is one the platform starts again by itself. Do not spend a retry budget on it: report it, and for a data vendor store your own key to keep working (`kipory-secrets`). `GET /v1/platform-status` says which platform accounts are `refusing` right now and since when, so you can tell "my flow broke" from "the platform is being topped up" without another failed run; while an account is refusing, an action on it fails at once, without the call. The same refusal on a key you stored reads `api-key-missing` or `quota-exhausted` instead, and is yours.
- **An action that produced nothing without failing.** A function whose vendor refused the call — a search the vendor rejected, a page read it would not serve, a file it could not parse — does not fail: the action reads `action-applied`, its output is empty and the run closes `succeeded`. The sign is an `action-warned` row naming that action, on every kind of run, a queued preview included: `detail.kind` is `function-soft-warning` and `detail.warningKind` is the function's own word for it (`SEARCH_FAILED`, `SCRAPE_FAILED`, `PDF_PARSE_FAILED`). Read the timeline for `action-warned` before trusting an empty output; `closing.warnings` on the run (`GET /v1/runs/{runId}`, and each row of `GET /v1/runs`) counts them by kind, so a run that warned can be told from one that did not without paging its log. `detail.message` is the function's own text — usually the vendor's reason, such as the values it accepts or a block on the page — cut to 500 characters (a refused key or an account out of credit is not a warning: it fails the action, see above — unless a fallback vendor answered for the platform's refused key, which reads `PROVIDER_FALLBACK`); an action that warned the same way earlier in the run carries `detail.messageRepeated: true` instead. Other `detail.kind` values are the engine's own warnings — `slot-conflict` and `slot-truncated` carry the slot in `detail.slot`; a `slot-truncated` row also says what was lost (`detail.originalSize` in characters, `detail.shape`, and `detail.elementsDropped` for a list — an object or a file is never cut: the action that produces one over the cap, a `flow.invoke` call included, fails instead; a list is not cut either unless its action says `"onOversize": "cut"` — by default it fails, as `"fail"` makes a text fail — and an action that says `"cut"` and names a `failureSlot` gets `code: "value-cut"` there when it was cut, so the flow itself can tell); `slot-near-limit` says an object, a file, or a list or text its action will not let be cut, is at least half the slot cap and was kept whole (`detail.originalSize` and `detail.limit` in characters; `detail.message` says what to change) — past the cap that action fails, so act on it while the run still succeeds; `fan-out-capped` says a fan-out was handed `detail.requested` items and ran `detail.branches`; `action-failed-continued` names the `detail.phase` of an action that failed under `"onFailure": "continue"` (the run then closes `partial`, not `succeeded`); and `file-not-kept` says the file the action produced was removed when the run ended (a run with no record keeps a file only when a `file.download-url` action made a link to it; `kipory-extract`).
- **"Could not look" and "looked, found nothing" are two kinds.** A function warning's `detail.warningKind` says which: a failure kind (`SEARCH_FAILED`, `FETCH_FAILED`, `SCRAPE_FAILED`, `RATE_LIMITED`) means the call did not complete — it is not saved, and an action with its own `tries` asks again; `NO_RESULTS` means the source was asked, answered, and had nothing — it is saved for the function's window and never retried; `NOT_FOUND` and `RESTRICTED` are a source saying outright that the thing does not exist or is not public. Treat `NO_RESULTS` from a scraped source (`web.search`) as "not known" rather than "none": a blocked results page finishes the same way.
- **Which action came back empty.** An action that ran and stored nothing is still `action-applied`; its row carries `detail.leftEmpty`, the output slots it left empty. That is the action to look at when a later one reads `action-skipped` for no visible reason: an action is skipped when none of its inputs is present, and an empty answer upstream is how that usually happens.
- **A saved answer keeps its warnings.** An action answered from its saved result (`detail.cacheHit: true`) repeats the saved value and the warnings it was saved with, so an empty answer served from the cache has the same `action-warned` row the first run had. Read the two together: an empty output on a `cacheHit` row means "this is what the earlier run got", not "the source was asked again"; `"reuseResultsForMinutes": 0` on the action asks again. An answer saved before warnings were kept still reads clean until its window ends.
- **A flow cannot read a warning.** Warnings are rows for a person or an agent to read after the run; an action downstream sees only what was stored in the slot. A source action that failed softly, one that found nothing, and one that was skipped all leave the same absent slot — unless the action names a `failureSlot`, which holds the softened failure, or `value-cut` when it says `"onOversize": "cut"` and its result was cut.
- **Longer error text.** Read the trace's `actionOutputs.writes[].error` (up to 2,000 characters, when the run was sampled) or, for a model action, `GET /v1/ai-calls?project={nodeId}&outcome=error&origins=all`.
- **A failed run with no failed action failed at apply.** When every action reads `action-applied`, the run closed `failed`, and `missingOutputs` is empty, the run's writes were refused as a set — a unique key another record holds, a write the platform refused, the effect cap. The closing (`closing.failure`, and the timeline's `run-finished` row) says which: its `cause` and `refusedWrite`. For the whole picture read `GET /v1/runs/{runId}/change-set`: `state` is `rejected`, `rejection.reason` names the class (`precondition-conflict`, `bound-exceeded`, `transaction-failed`, `invalid-effect`), `rejection.cause.kind` the refusal (`natural-key-collision`, `unique-violation`, `write-refused`, `database-error`) and `rejection.cause.actionId` the action that staged the refused write. Nothing was written.
