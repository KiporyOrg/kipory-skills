# Reading a run's timeline

What each part of a run's timeline tells you, and what to do about it. `SKILL.md` lists these by their first line, under "The sequence".

- **Which step a row is about.** Each row names its step by `stepKey` and `stepName` (the name as it was when the run happened), and `flowId` the flow that holds it, so a sub-flow's steps are told from the caller's; all three are null on the run's own rows (`run-started`, `run-finished`). Inside an `each` or a `repeat`, `branchId` names the element's run and `branchPathIds` lists the blocks around it, outermost first — an `each` level with the `index` of the element it ran for, a `repeat` level with its `iterationIndex`. `GET /v1/runs/{runId}/spend` keys its `byStep` entries by the same `flowId` and `stepKey`, so the two reads join on them.
- **Why a step failed.** Its `step-failed` row says so under `detail`: `detail.phase` (`function-error`, `condition-error` for an `if` test or a `repeat`'s `until` that threw, `sub-flow-failed`, `platform-fault`, `target-unreachable` for an address whose name did not resolve — the site is gone, nothing was blocked — `ssrf-blocked` for an address the platform refuses, …) and `detail.message`, the step's error text cut to 500 characters (an ellipsis marks the cut; a step that failed the same way earlier in the run carries `detail.messageRepeated: true` instead), beside `detail.tries` (only when the step was tried more than once) and `detail.cacheHit` / `detail.rateLimitWaitMs` when they apply. A failure no `try` catches fails the run; one a `try` catches runs that `try`'s `catch` steps, where `error` holds its `code`, `message` and `step`.
- **`platform-fault` is not yours to fix.** A step that failed with `detail.phase: "platform-fault"` ran on one of the platform's own accounts — a vendor refused the platform's key or its account is out of credit, or a model provider's account is exhausted — and `detail.message` ends "This is a platform fault, not a fault in the flow" (a model call reads `… provider account exhausted (quota/billing)`). The run's class is `platform-account`, and its code says which: `vendor-out-of-credit` or `credential-rejected`. The step is not charged, the deployment's operator is alerted by the same failure, and a later run succeeds once the account is topped up. An unattended run is not started again on it — it fails at once, and the project hears `platform/vendor.unavailable` when a data vendor's account stops serving and `platform/vendor.available` when it serves again. Do not spend a retry budget on it. Check `GET /v1/platform-status` (below) first: when it does not already show the account refusing, file one report with `POST /v1/reports` for the outage, not one per run, with the run ids in `runIds` (`kipory-connect`, "When something stops you"). For a data vendor, store your own key to keep working (`kipory-secrets`). `GET /v1/platform-status` says which platform accounts are `refusing` right now and since when, so you can tell "my flow broke" from "the platform is being topped up" without another failed run; while an account is refusing, a step on it fails at once, without the call. The same refusal on a key you stored reads `api-key-missing` or `quota-exhausted` instead, and is yours.
- **A throttled platform account** reads `detail.phase: "function-error"` with code `rate-limited`; the run's class is `platform-account` too, and an unattended run is started again by the platform.
- **A model provider failing on its side** fails the step with the provider's own words in `detail.message` — `HTTP 503`, `model_unavailable`, `upstream connect error`, `fetch failed`. That is an outage at the provider, not your flow, and a key you stored does not help. `GET /v1/platform-status` reads that provider `degraded` with `since` once at least five of its calls in the last 30 minutes failed this way and they are over half of its calls; one stray 503 does not move it, and it reads `ok` again about 10 minutes after calls are answered again. While it is `degraded`, run again later or move the task to a model on another provider (`kipory-build`'s `references/models.md`); do not file a report for it. A run that failed this way while the read says `ok` is worth one report. A throttled call (`429`) or one past the task's time limit is not this: those can be your key's or your configuration's. **A data vendor** (the account behind `x.posts`, a scraper, a search) failing on its side is not measured at all: platform-status reads it `ok` unless the vendor refuses the platform's key, so a run of `vendor-unavailable` failures on one vendor while it reads `ok` is worth one report.
- **A step whose required input was missing.** Nothing is skipped silently: a step whose required read finds nothing fails with `STEP_INPUT_ABSENT`, and one whose input must not be empty and is fails with `STEP_INPUT_EMPTY` — before its function runs, so nothing is charged. The save proves every read it can, so this usually means a value the save could not see into: a field of an untyped value, or data that changed shape. Fix the flow, not the data: guard the step with an `if` and `{has: …}` / `{filled: …}`, or read `{path, optional: true}` or `{path, default: …}` (`kipory-build`).
- **A step that did not run.** A `step-not-run` row says a step was reached and did not run; `detail.notRun` says why — `branch-not-taken` (its `if` branch was not taken), `flow-returned` (a `return` ended the flow first), `block-failed` (the block around it failed), `caught` (a `try` caught a failure before it), `disabled` (it is switched off), `run-cancelled`, or `applied-earlier` (a record retried after an earlier attempt applied the step: it is not run or charged twice). None of those is a failure of that step.
- **A step that gave an empty answer without failing.** A function whose vendor refused the call — a search the vendor rejected, a page read it would not serve, a file it could not parse — does not fail: the step reads `step-applied`, its output is empty and the run closes `succeeded`. The sign is an `step-warned` row naming that step, on every kind of run, a queued preview included: `detail.kind` is `function-soft-warning` and `detail.warningKind` is the function's own word for it (`SEARCH_FAILED`, `SCRAPE_FAILED`, `PDF_PARSE_FAILED`). Read the timeline for `step-warned` before trusting an empty output; `closing.warnings` on the run (`GET /v1/runs/{runId}`, and each row of `GET /v1/runs`) counts them by kind, so a run that warned can be told from one that did not without paging its log. `detail.message` is the function's own text — usually the vendor's reason, such as the values it accepts or a block on the page — cut to 500 characters (a refused key or an account out of credit is not a warning: it fails the step, see above — unless a fallback vendor answered for the platform's refused key, which reads `PROVIDER_FALLBACK`); a step that warned the same way earlier in the run carries `detail.messageRepeated: true` instead. Other `detail.kind` values are the engine's own warnings: `slot-truncated` says a value was cut to the size one value may hold (`detail.originalSize` in characters, `detail.shape`, and `detail.elementsDropped` for a list) — an object or a file is never cut: the step that produces one over the cap fails instead, a `flow.invoke` call included; a list is not cut either unless its step says `"onOversize": "cut"`; `slot-near-limit` says a value its step will not let be cut is at least half that cap and was kept whole (`detail.originalSize` and `detail.limit`; `detail.message` says what to change) — past the cap that step fails, so act on it while the run still succeeds; `repeat-exhausted` says a `repeat` stopped without `until` holding — at its `max` under `onMax: "stop"`, or when the payer's credit ran out between passes (`detail.reason`, `detail.iterations`); `each-capped` says an `each` was handed `detail.requested` elements and ran `detail.branches`; and `file-not-kept` says the file the step produced was removed when the run ended (a run with no record keeps a file only when a `file.download-url` step made a link to it; `kipory-extract`).
- **"Could not look" and "looked, found nothing" are two kinds.** A function warning's `detail.warningKind` says which: a failure kind (`SEARCH_FAILED`, `FETCH_FAILED`, `SCRAPE_FAILED`, `RATE_LIMITED`) means the call did not complete — it is not saved, and a step with its own `tries` asks again; `NO_RESULTS` means the source was asked, answered, and had nothing — it is saved for the function's window and never retried; `NOT_FOUND` and `RESTRICTED` are a source saying outright that the thing does not exist or is not public. Treat `NO_RESULTS` from a scraped source (`web.search`) as "not known" rather than "none": a blocked results page finishes the same way.
- **How big each step's value was.** An `step-applied` row of a function step (not `flow.invoke`) carries `detail.sizes`: `characters` (a text's length, or a list's or object's length as JSON, the unit the size cap counts) and `items` for a list — never any of the value. Read it beside `durationMs` to find the step that got slow because its input grew.
- **Which step came back empty.** A step that ran and gave nothing is still `step-applied`, with `detail.answeredNothing: true`; its row carries `detail.leftEmpty`, the value it left empty. That is the step to look at when a later one fails with `STEP_INPUT_ABSENT`: a required input that is nothing fails the step that reads it, and an empty answer upstream is how that usually happens.
- **A saved answer keeps its warnings.** A step answered from its saved result (`detail.cacheHit: true`) repeats the saved value and the warnings it was saved with, so an empty answer served from the cache has the same `step-warned` row the first run had. Read the two together: an empty output on a `cacheHit` row means "this is what the earlier run got", not "the source was asked again"; `"reuseResultsForMinutes": 0` on the step asks again. An answer saved before warnings were kept still reads clean until its window ends.
- **A flow cannot read a warning.** Warnings are rows for a person or an agent to read after the run; a later step sees only the value. A source step that failed softly and one that found nothing both give an empty or missing value: test it with `filled` or `has` in an `if` before you use it, and read the timeline when you need to know which it was.
- **Longer error text.** Read the trace's `stepOutputs.writes[].error` (up to 2,000 characters, when the run was sampled) or, for a model step, `GET /v1/ai-calls?project={nodeId}&outcome=error&origins=all`.
- **A failed run with no failed step failed at apply.** When every step reads `step-applied`, the run closed `failed`, and `missingOutputs` is empty, the run's writes were refused as a set — a unique key another record holds, a write the platform refused, the effect cap. The closing (`closing.failure`, and the timeline's `run-finished` row) says which: its `cause` and `refusedWrite`. For the whole picture read `GET /v1/runs/{runId}/change-set`: `state` is `rejected`, `rejection.reason` names the class (`precondition-conflict`, `bound-exceeded`, `transaction-failed`, `invalid-effect`), `rejection.cause.kind` the refusal (`natural-key-collision`, `unique-violation`, `write-refused`, `database-error`, `one-term-vocabulary` — with `vocabularyKey` and the `terms` a vocabulary that admits one term could not hold, `timed-out` — saving the run's changes took longer than one save may, `budgetMs`; the platform's, and the run is not started again, so stage fewer changes per run) and `rejection.cause.stepKey` the step that staged the refused write. Nothing was written.
