# What will bite you — diagnosing a run

Each bullet is a trap met while diagnosing a run: what happens, and what to do about it. `SKILL.md` lists them by their first line.

- **Three silent things stand between a run and a trace.** _Sampling_: per project, per path — request-driven runs and record processing each have a rate, and the listing returns them; at `0.05` a flow that ran two hundred times leaves about ten traces, at `0` none while working perfectly; `eval` and `manual` traces are always captured. _Expiry_: seven days by default; a 404 on yesterday's id is the reaper. _The row budget_: a run whose values do not fit even after truncation is dropped **whole**, indistinguishable from not being sampled.
- **`null` and `0` in the sampling rates mean opposite things.** Null inherits the deployment default — tracing is on, but sampled: by default about half of request-driven runs and a tenth of record-processing runs keep a trace. Zero records nothing. The rates are the platform operator's to set; no project role or key can change them. A run that was not sampled answers `404 No trace is retained for run …`; its timeline and change set are still there. To see the values, queue a preview of the same inputs (`POST /v1/flows/{id}/preview-runs` with `apply: false`) and read that run's `/trace`, or read the `action-ended` frames of the preview stream. The plain preview response carries `flowOutput` and a transcript, not the slot values.
- **A trace has no status field, and a whole `output` does not mean the run succeeded.** The flag is per action: `actionOutputs.writes[]` with `kind: "failed"` and its `error`. An action that fails after the bound slots were written — an `event.emit`, a late write — leaves `output` complete on a run that answered 502, so read the writes (or the timeline) before `output`. Under `fail-run` the actions that do not depend on the failed one still run and log `action-applied`; its dependents skip. The first `action-failed` row is the cause, and a later `action-applied` is not evidence the run recovered. `actionOutputs: null` means that writer recorded no writes; an empty array means it recorded and there were none.
- **The timeline is complete where the trace is not.** `paging.total` counts recorded events and `truncated` says events happened past the writer's bound; both can be true. `after` on the timeline means _later_; on the runs list it means _older_. `run-aborted` is an ending from outside, not a failure of the flow. `action-not-reached` means the action's branch never materialized — not a skip. `log-truncated` means rows past the per-run cap were dropped: an incomplete timeline, not a short one. An `action-skipped` with no `detail` was stopped by its condition, by a missing required input, or by the payer running out of credit part-way through the run, and the row does not say which; only a projection miss carries `detail`. When a run ends in a tail of bare skips — every action after some point — suspect credit: read `status` on the balance (`kipory-operate`).
- **`closing: null` on a run is three facts at once** — in flight (a run with `waiting` set, about to be started again, is one of these), crashed with its buffer, or reaped — and `lifecycle: unknown` means no outcome was recorded, never finished. A synchronous endpoint call and a preview have no invocation row: each reads `unknown` until its closing frame lands and `settled` after, so `closing` non-null is the test that such a run ended. `flow.label` is a live read, so a relabelled flow reports its new label on an old run; `flow: null` means the flow is gone. Only `flow-snapshots` says what graph actually ran — its actions only: the flow's `outputBinding` is not in it, so a binding fault is `GET /v1/flows/{id}/health`'s to name.
- **The runs list has no status or trigger filter**, deliberately; `GET /v1/failed-runs` is the filtered read of what failed. `declaredActions` is a floor: fan-out branches and sub-flows are uncounted, so `actionsStarted` can exceed it.
- **Read `source`, not `trigger`, for what started a run.** `source.kind` is `schedule`, `trigger`, `endpoint`, `record`, `request`, `preview` or `unknown`, with `targetId`. A synchronous or streaming endpoint call reads `request`, with the endpoint's key as `targetId`; an async endpoint call reads `endpoint`, with the endpoint's key too. To count calls, send `starters=1` with a `window`: the answer's `starters` has one row per starter with `runs`, `failedRuns` and `lastStartedAt`; one endpoint's calls are its key's rows under `request`, `endpoint` and `public` summed. A `request` with `targetId: null` is a run stored before the key was recorded, or one no endpoint started. `trigger` (and `detail.trigger.kind` on the timeline's `run-started`) is the stored vocabulary: `request` for a sync or streaming call, and `endpoint` for an async call and for a schedule's or a trigger's fire, whose id is `schedule:<id>` or `trigger:<id>`.
- **A slow sync call is not always a slow model.** A `text.generate` action (and the other ingest-phase actions) queues on the ingest worker, and its `durationMs` in the timeline counts the queue wait — which is not billed: the action's `function-run` entry on `GET /v1/runs/{runId}/spend` gives the seconds it was charged. `latencyMs` on the matching row of `GET /v1/ai-calls?project={nodeId}` is the model's own time; the difference is queue. A sync endpoint that 504s at its `syncTimeoutMs` (30 s by default) on a busy worker needs a higher timeout or an async endpoint, not a faster model.
- **Records stuck `indexState: never` or a `vectorProgress` that does not move is an embedding failure you will not see on the record.** Read `GET /v1/ai-calls?project={nodeId}&origins=projection&outcome=error` — a provider quota error there is retried three times within about fifteen seconds, then only by the daily re-index sweep (08:00 UTC), and never surfaces anywhere else.
- **`GET /v1/runs/{runId}/spend` answers an empty breakdown, not a 404, for a real run.** A run that spent nothing and one whose spend aged out both return an empty breakdown; an id with no timeline — an unknown id, or an inline preview's `previewSessionId` — is a 404 like the other run reads. An inline preview's cost is read from `GET /v1/projects/{nodeId}/usage/events?scope=design` instead; a queued preview's run answers `/spend` like any run. `actionId: null` is the unattributed bucket.
- **`credits: 0` on an action is not always a free action.** Each `/spend` entry, and the run, carries `uncharged`: how many of its `events` the platform paid for. `credits: 0` with `uncharged` equal to `events` is work nobody was charged for — the same action costs credits in a charged run. `credits: 0` with `uncharged: 0` is a real zero (`kipory-operate`'s `references/spend.md`).
- **A 402 is not a flow problem, and at admission it leaves no run to read.** Five codes say it <!-- count: api-402-codes --> — the wallet, a person's own ceiling, a member's own wallet, the project's design-time ceiling, and a public endpoint's one answer for its wallet or its public spend cap — and the remedies do not substitute. Branch on the error `code` (`kipory-operate`). A wallet that empties part-way through a run is different: the run exists, the actions after that point read `action-skipped`, and it ends short — often `FLOW_OUTPUT_MISSING` — with no action failed.
- **Which actions processing actually runs is a read.** `GET /v1/flows/{id}/coverage` reports which actions of a flow, and of the flows it invokes, ran across the record-processing attempts since the graph last changed — from the per-attempt record every processing run writes, so trace sampling does not thin it. It covers the newest `attemptLimit` attempts (500 by default; `truncated` says when there were more), and it measures execution, not correctness: an action that never ran there is a branch none of those attempts reached (fields: `kipory-build`'s `references/api/flows.md`).
- **A flow that saved with blocking issues still runs**, because nothing re-checks the graph at run time; its trace is usually the fastest way to see what the diagnostic predicted. A flow that would not save never ran — that is `kipory-build`.
- **To reproduce, take a trace's `inputs` to a preview** (as `input.inputs` beside `"kind": "slots"`) — but a preview is not a rehearsal: it bills and **applies the writes it stages** unless `apply: false`. Reproducing a bad run against a live project without that flag writes real records a second time. An async endpoint run can also be run again as it was: `POST /v1/runs/{runId}/retries` (ADMIN) answers 202 with a new `runId` — a real run that writes and is charged; a run that is not an endpoint invocation answers 409 (re-run a record with `POST /v1/records/{id}/reprocess`).
- **`GET /v1/activity/stream?project=` tells you that something moved**, in five domains — eval runs, flow runs, schedule runs, endpoint calls, record ingestion — and carries no ids at all. It is a signal to go read, not a feed of runs.
