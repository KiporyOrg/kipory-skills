# What will bite you — diagnosing a run

Each bullet is a trap met while diagnosing a run: what happens, and what to do about it. `SKILL.md` lists them by their first line.

- **Working around a problem in silence.** Kipory cannot fix what nobody tells it. When something on Kipory stops you — an unexpected error, a doc that said something untrue, a capability you need that is missing — file a report with `POST /v1/reports`, then carry on with your workaround. When and how: `kipory-connect`, "When something stops you".
- **Three silent things stand between a run and a trace.** _Sampling_: per project, per path — request-driven runs and record processing each have a rate, and the listing returns them; at `0.05` a flow that ran two hundred times leaves about ten traces, at `0` none while working perfectly; `eval` and `manual` traces are always captured, and so is every run that processed a record, or ran asynchronously (an async endpoint call, a schedule, a trigger), in which a step failed — whether it stopped the run or a `try` caught it — unless the rate is `0`; sync and stream calls stay sampled, and the row budget can still drop it. _Expiry_: seven days by default; a 404 on yesterday's id is the reaper. _The row budget_: a run whose values do not fit even after truncation is dropped **whole**, indistinguishable from not being sampled.
- **`null` and `0` in the sampling rates mean opposite things.** Null inherits the deployment default — tracing is on, but sampled: by default about half of request-driven runs and a tenth of record-processing runs keep a trace. Zero records nothing. The rates are the platform operator's to set; no project role or key can change them. A run that was not sampled answers `404 No trace is retained for run …`; its timeline and change set are still there. To see the values, queue a preview of the same inputs (`POST /v1/flows/{id}/preview-runs` with `apply: false`) and read that run's `/trace`, or read the `step-ended` frames of the preview stream (each carries that step's value as `slotBag`). The plain preview response carries `flowOutput` and a transcript, not the values.
- **A trace has no status field, and a whole `output` does not mean the run succeeded.** The flag is per step: `stepOutputs.writes[]` with `kind: "failed"` and its `error`. A step that fails after the `return` value was built — an `event.emit`, a late write — leaves `output` complete on a run that answered 502, so read the writes (or the timeline) before `output`. Inside a `parallel` block the siblings of a failed step may still finish and log `step-applied`. The first `step-failed` row is the cause, and a later `step-applied` is not evidence the run recovered. `stepOutputs: null` means that writer recorded no steps; an empty `writes` array means it recorded and there were none.
- **The timeline is complete where the trace is not.** `paging.total` counts recorded events and `truncated` says events happened past the writer's bound; both can be true. `after` on the timeline means _later_; on the runs list it means _older_. `run-aborted` is an ending from outside, not a failure of the flow. `step-not-run` means the step was reached and did not run — its branch was not taken, a `return` came first, its block failed — never that its input was missing: a missing required input fails the step. `log-truncated` means rows past the per-run cap were dropped: an incomplete timeline, not a short one. A run that ends short with no failed step may have had its payer run out of credit part-way: read `status` on the balance (`kipory-operate`).
- **`closing: null` on a run is three facts at once** — in flight (a run with `waiting` set, about to be started again, is one of these), crashed with its buffer, or reaped — and `lifecycle: unknown` means no outcome was recorded, never finished. A synchronous endpoint call and a preview have no invocation row: each reads `unknown` until its closing frame lands and `settled` after, so `closing` non-null is the test that such a run ended. `flow.label` is a live read, so a relabelled flow reports its new label on an old run; `flow: null` means the flow is gone. Only `flow-snapshots` says what each flow looked like when it ran.
- **The runs list has no status or trigger filter**, deliberately; `GET /v1/failed-runs` is the filtered read of what failed. `flowKey` lists every run that ran the flow — as its own flow, or as a sub-flow that started at least one step — each once, under the flow that started it; `record={id}` lists the runs that processed one record. A run's count of the steps it declares is a floor: the runs of an `each` and of sub-flows are uncounted, so the steps it started can exceed it.
- **Read `source`, not `trigger`, for what started a run.** `source.kind` is `schedule`, `trigger`, `endpoint`, `record`, `request`, `preview`, `eval` (one case of an eval run, whose id is the `targetId` on a list row; `starters` counts all eval cases in one row with `targetId: null`, as it does records) or `unknown`, with `targetId`. A synchronous or streaming endpoint call reads `request`, with the endpoint's key as `targetId`; an async endpoint call reads `endpoint`, with the endpoint's key too. To count calls, send `starters=1` with a `window`: the answer's `starters` has one row per starter with `runs`, `failedRuns` and `lastStartedAt`; one endpoint's calls are its key's rows under `request`, `endpoint` and `public` summed. A `request` with `targetId: null` is a run stored before the key was recorded, or one no endpoint started. `trigger` (and `detail.trigger.kind` on the timeline's `run-started`) is the stored vocabulary: `request` for a sync or streaming call, and `endpoint` for an async call and for a schedule's or a trigger's fire, whose id is `schedule:<id>` or `trigger:<id>`.
- **A slow sync call is not always a slow model.** A `text.generate` step (and the other ingest-phase steps) runs inside the call itself, and its `durationMs` in the timeline counts any wait for a free slot on the server or for another identical call already in flight — which is not billed: the step's `function-run` entry on `GET /v1/runs/{runId}/spend` gives the seconds it was charged. `latencyMs` on the matching row of `GET /v1/ai-calls?project={nodeId}` is the model's own time; the difference is waiting. A vendor read that has to wait on the vendor for more than a few seconds finishes in the background and the call waits for it. A sync endpoint that 504s at its `syncTimeoutMs` (30 s by default) needs a higher timeout or an async endpoint, not a faster model.
- **Records stuck `indexState: never` or a `vectorProgress` that does not move is an embedding failure you will not see on the record.** Read `GET /v1/ai-calls?project={nodeId}&origins=projection&outcome=error` — a provider quota error there is retried three times within about fifteen seconds, then only by the daily re-index sweep (08:00 UTC), and never surfaces anywhere else.
- **`GET /v1/runs/{runId}/spend` answers an empty breakdown, not a 404, for a real run.** A run that spent nothing and one whose spend aged out both return an empty breakdown; an id with no timeline — an unknown id, or an inline preview's `previewSessionId` — is a 404 like the other run reads. An inline preview's cost is read from `GET /v1/projects/{nodeId}/usage/events?scope=design` instead; a queued preview's run answers `/spend` like any run. `stepKey: null` is the unattributed entry: spend made outside any step.
- **`credits: 0` on a step is not always a free step.** Each `/spend` entry, and the run, carries `uncharged`: how many of its `events` the platform paid for. `credits: 0` with `uncharged` equal to `events` is work nobody was charged for — the same step costs credits in a charged run. `credits: 0` with `uncharged: 0` is a real zero (`kipory-operate`'s `references/spend.md`).
- **A 402 is not a flow problem, and at admission it leaves no run to read.** Five codes say it <!-- count: api-402-codes --> — the wallet, a person's own ceiling, a member's own wallet, the project's design-time ceiling, and a public endpoint's one answer for its wallet or its public spend cap — and the remedies do not substitute. Branch on the error `code` (`kipory-operate`). A wallet that empties part-way through a run is different: the run exists and ends short, and its timeline is there to read.
- **Which steps processing actually runs is a read.** `GET /v1/flows/{id}/coverage` reports which steps of a flow, and of the flows it invokes, ran across the record-processing attempts since the flow last changed — from the per-attempt record every processing run writes, so trace sampling does not thin it. It covers the newest `attemptLimit` attempts (500 by default; `truncated` says when there were more), and it measures execution, not correctness: a step that never ran there is a branch none of those attempts reached (fields: `kipory-build`'s `references/api/flows.md`).
- **A flow can turn red after it saved.** A save refuses any error, so a flow that saved proved every read then; a rule a later platform build adds can still mark it red while its runs go on. `GET /v1/flows/{id}/health` names it, and its trace is usually the fastest way to see what the finding predicted. A flow that would not save never ran — that is `kipory-build`.
- **To reproduce, take a trace's `inputs` to a preview** (as `input.inputs` beside `"kind": "slots"`, keyed by the flow's input names) — but a preview is not a rehearsal: it bills and **applies the writes it stages** unless `apply: false`. Reproducing a bad run against a live project without that flag writes real records a second time. An async endpoint run can also be run again as it was: `POST /v1/runs/{runId}/retries` (ADMIN) answers 202 with a new `runId` — a real run that writes and is charged; a run that is not an endpoint invocation answers 409 (re-run a record with `POST /v1/records/{id}/reprocess`).
- **`GET /v1/activity/stream?project=` tells you that something moved**, in five domains — eval runs, flow runs, schedule runs, endpoint calls, record ingestion — and carries no ids at all. It is a signal to go read, not a feed of runs.
