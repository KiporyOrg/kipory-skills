# What will bite you — exposing a flow over HTTP

Read this before you save an endpoint or when a call to one surprises you: each bullet is a trap met while putting a flow on HTTP, with what to do about it.

- **Working around a problem in silence.** When something on Kipory stops you — an unexpected error, a doc that said something untrue, a capability you need that is missing — file a report: `kipory-connect`, "When something stops you".
- **A refused save is one 422 `VALIDATION_FAILED` with `details.issues[]`, every issue in one shape: `{ instancePath, keyword, params, message, in }`**, `in` saying whether it is in the `body`, the `query` or the `path` — the shape every 422 the platform answers uses, a product endpoint's included. A body the request schema refuses — an unknown key, a wrong type, a path the pattern refuses such as `{user_id}` — gives just that; `instancePath` is where, and `message` may be as short as `Invalid`. A config rule — a binding to an undeclared parameter, an unbound required slot, async without 202 — adds `code`, `remedy` (the fix, when it has one) and `field` (in body terms, only when one field caused it). `ENDPOINT_CONFIG_INVALID` is several rules under one code — a provider slot bound or returned, async on a GET or without 202, a method or path the contract refuses — so read its `remedy` and `field` to tell them apart. Branch on `code` where there is one, never on `message`. A path collision or duplicate key on a real save is a 409 `CONFLICT` with no `details`, told apart only by the suffix in the message; the `validateOnly` verdict reports the same two as findings on `contractConfig.path` and `endpoint`.
- **`successStatus` defaults to 200 and async demands 202.** Omitting it on an async endpoint is a 422 naming the number, not the field. `execution` has no default. `deltaSlot` must be sent, even as `null`: a missing key is refused (its message says `null` is accepted), while `"deltaSlot": null` is valid and streams no deltas.
- **An endpoint's key is also its method name in the project's API document**, in camelCase: `list-items` publishes `listItems`, which a generated client calls. Two keys that differ only in dots, dashes and underscores (`list-items` beside `list_items`) give one name, so the second is refused at create, a 422 issue on `key`. A key that would start with a digit, or look like a platform route's name (`getV1Runs`), is published with an `endpoint` prefix.
- **A path parameter name is letters and digits only** — `{userId}` yes, `{user_id}` no — even though the endpoint key may carry dots and hyphens.
- **There is no read-only flag to set; who may call is derived.** An async invoke or a DELETE is a write; any other GET is a read; anything else is a write when its bound flow reaches an action that changes data — a function that writes, an event emitted beyond the run (it can start triggers), or a vocabulary resolution. An async invoke cannot be saved on GET. Every endpoint read carries `access`, which says which.
- **An endpoint is public only when you say so, and then the project pays for every call.** `contractConfig.auth: "none"` makes it callable with no key and no session — for a landing page's list, a sign-up form, a public search. Three things must hold or the save is a 422: the target is a synchronous `flow.invoke` (issue code `PUBLIC_ENDPOINT_KIND_UNSUPPORTED`), the flow needs no signed-in user (`PUBLIC_ENDPOINT_NEEDS_USER` — its signature does not take the calling user and `access.requiresUser` is false; an action that only reads `userInfo` without the flow declaring it still saves, and finds no user when called), and the project has already set `publicSpendCapCredits` on `PATCH /v1/projects/{nodeId}/settings` (`PUBLIC_SPEND_CAP_REQUIRED`) — the most public calls may spend per UTC day, where `0` refuses them all. A public endpoint reads no credential: a key or cookie sent along is ignored, the run has no user, `Idempotency-Key` is ignored, and any origin may call it from a browser — without credentials, so a page must not send `credentials: "include"`. It has its own limits (`contractConfig.publicRpm`, 60 a minute unless you set it; an allowance per caller address; a 256 KB body) and answers `402 PUBLIC_ENDPOINT_UNAVAILABLE` with no `details` when the wallet or the cap refuses, or when the project cannot serve it (it is suspended, or the flow needs a signed-in user). Run `validateOnly` first: it warns `PUBLIC_ENDPOINT_SPENDS`, naming the model and vendor actions a stranger can make you pay for, `PUBLIC_ENDPOINT_WRITES` when the flow changes data, and `PUBLIC_ENDPOINT_NAMES_PERSON` when a read takes its `userId` from the request, which lets anyone read anyone's records. It can be a webhook receiver: bind the signature header and the raw body and check them with `request.verify-signature`, which answers 401 when they do not match.
- **Which credential it takes is derived too.** `access.requiresUser` is true when the bound flow reads or writes records owned by a user: a key acts as the project and has no user, so its call is refused `403` before the flow runs. `access.requiresUserBy` names the functions (`events.subscribe` for a subscription to a user-scoped channel, which is refused the same way). An action counts wherever it sits, so one flow cannot serve a key on one branch and a signed-in user on another — give the key its own endpoint and flow. `kipory-build` has the recipes (its `references/endpoint-answers.md`, §8): two endpoints for shared data with a personal extra or for anonymous and signed-in callers, and a `userId` bound from a path parameter for a key reading on a named user's behalf.
- **A list or a lookup is a view endpoint: declare its path and nothing else.** A `GET`, synchronous `flow.invoke` over a flow that answers one `record.view` page unchanged takes its query from the view — the view's params, typed and bounded, plus `after`, `before` and `limit` — answers `{ items, nextCursor, prevCursor, paging: null }` (a `one` view: the record, or `404`), and, when the flow is that one action fed only by the request, an `ETag` a client sends back as `If-None-Match` for a `304` that runs and charges nothing. Declare no query params and no `inputs` for it; declaring `after`, `before` or `limit` yourself makes it an ordinary endpoint, with the plan warning `VIEW_ENDPOINT_NOT_DERIVED`. The view and the flow are `kipory-build`'s (`references/views.md` and `view-endpoints.md`, §11); `references/packs/api-endpoints-anatomy.md` has the derived contract.
- **`shadowedBy: null` is a verdict, not unknown**, and per-project route enablement does not affect it: a disabled coded group 404s by hook but its route stays registered and still wins the match. A coded **literal** route that takes one value of a parameter is not a shadow and sits in `partiallyShadowedBy` instead. You meet it on a path whose first segment is a parameter (`/v1/{kind}/stats` saves; coded routes answer some `kind`s first), or on an endpoint stored before the reserved-word rule.
- **A coded route shipped later kills your endpoint with no error anywhere.** The save-time check is half the guarantee; re-read with `expand=shadowed` after a deployment moves.
- **Route enablement toggles coded route groups, not endpoints.** `POST /v1/route-enablement { project, group, enabled }`. Only `auth`, `account`, `usage`, `files` and `docs` are toggleable; the group owns its whole top-level segment (which is why the save refuses an endpoint under it), and disabling `usage` takes the credit balance your product reads. The last group cannot be turned off; a change is not a security boundary, and it takes a little over 30 seconds to reach every request (each api process holds the setting for 30 s), so wait about 45 s before testing it.
- **An `events.subscribe` endpoint refuses a key on `user` and `record` scope** with 403; only `project` scope is expressible for a machine caller. A `record` scope needs `id: { from: "path.<name>" }`. A `categoryKey` or event key the project does not have is refused `SUBSCRIBE_EVENT_UNKNOWN` on `targetConfig.source.categoryKey` (or `targetConfig.source.eventKeys[i]`).
- **`flow.stream` `retry.onDiscard` is `suppress`.** Under `suppress`, `stage` frames stream live for every attempt but `delta` frames are held and sent only for the winning attempt, so a retrying endpoint streams no text until an attempt wins.
- **`delta` frames come from `text.generate` actions with structured output.** While a run goes, the stream takes text from the string field named `deltaSlot` in **any** `text.generate` action's output as the model writes it — an action inside a sub-flow the flow invokes included — it does not check which action feeds the flow output, so an unbound action with a field of that name streams too. One stream per attempt: text that does not extend what was already sent is dropped, so a loop, or two such actions, streams only the first draft, and later drafts arrive only in `result` — which is why the deltas a client shows can differ from the refined `result` it ends on. Stream from one action that runs once, with a field name no other generate action uses. An action returning plain text, and every other function, streams no deltas: the client gets `stage` frames, then the whole value in `result`. Write the client to cope with zero deltas. The save refuses a `deltaSlot` that is not a flow output (`ENDPOINT_INPUT_UNSATISFIED`) and one no action can stream — not a string field of any structured `text.generate` action's output (`ENDPOINT_DELTA_SLOT_NOT_STREAMABLE`) — in `validateOnly` and a document plan alike.
- **A `flow.stream` failure is HTTP 200 with an `error` frame.** Once hijacked the status is fixed; the frame `code` is the only signal. Every stream ends with `done` — after `result` on success, after `error` or `close` otherwise — so `done` alone says nothing about how it went.
- **A sync timeout (504) stops the run at its next action and discards its staged writes, but not its bill** — paid calls already made stay charged, and unstaged writes (vector points, files, minted terms) stand. A timeout that lands after the last action, while the writes are being committed, lets them land anyway, so retrying without an `Idempotency-Key` can double-apply (`references/consumer.md`, Headers worth knowing, says what the key guarantees for each kind of target). A `flow.stream` that ends early (client gone, deadline, revoked session) discards its staged writes the same way.
- **The 202's `statusPath` is relative.** Join it against the project host, not the api host.
- **A malformed stored auth config re-enables Google sign-in.** The read reports `malformed: true` and nothing else does; treat it as urgent.
- **A VIEWER key making a call that counts as a write is a 403** indistinguishable from a VIEWER session's — and a default key is VIEWER. Read the endpoint's `access` before handing a VIEWER key to a caller.
- **`GET /v1/api-endpoints/{id}` on a row whose config no longer parses is a 500**, not a partial body; only the list degrades into `unreadable`.
