How a request to `<baseUrl>/v1/<your-path>` is served. This is what your product's client — or your own agent calling the product — needs to know. The design API on the api host is `kipory-connect`'s subject, not this file's.

- **`baseUrl` is the project's own origin.** Read it from `GET /v1/projects/{nodeId}` or from the project's entry in `GET /v1/grant`; an endpoint's `invokeUrl` is `baseUrl` plus its path. Do not infer either from the base URL you were handed: they follow the deployment's own configured address (`kipory-connect`'s `references/conventions.md` owns the two-hosts rule).
- **Where it is `null`** — a deployment configured on a bare `localhost`, with no host name to derive a project host from — send the same request to the api's base URL with the header `x-kipory-project-slug: <project slug>`; without it that host answers 404 `No project matched this request's host`, naming the header. That header is read on a local or development stack only; a production deployment never reads it.
- **A response is JSON or server-sent events.** No endpoint answers HTML, a redirect or a file.

## Matching

- One catch-all serves every method under `/v1/`. A **coded route always wins** over it; among your endpoints, fewer path params wins, then more literal characters, then the endpoint key.
- Method is matched, not leaked: the right path with the wrong method is the same 404 as no path. A path over 2048 characters is a 404. Any `/v1/_…` path other than the built-in invocation status is a 404.
- The write gate runs **after** matching, so an unknown path 404s rather than revealing itself as a 403.

## Credentials

Three, resolved in this order from one hook:

1. `Authorization: Bearer <api-key>` — a machine key. Its grant must **reach** the project, else 403 `FORBIDDEN` (`Token is not valid for this API`). A key never has a user: its runs are project-owned, it gets no `userInfo`, and it is refused by any flow that reads or writes person-owned records.
2. `Authorization: Bearer <session-token>` — the opaque token a native app receives on sign-in, or an app on the project's own proven domain receives from `POST /v1/auth/handoff/exchange` (that one works on this project's host only); presented verbatim.
3. The session cookie — a browser user.

An `Authorization` header present but not `Bearer …` is an immediate 401 with no fall-through to the cookie. A session's user must still be active and a member of the project on every request; a key has no such third party.

A VIEWER principal — session or key — is refused on any call that counts as a write: 403 `FORBIDDEN`, whose message names the credential — `This API key's role (viewer) can only read …` for a key, `Your role (viewer) is read-only …` for a session. An async invoke or a DELETE always counts; any other GET never does; anything else does when the endpoint's bound flow reaches a step that changes data — a handler that writes, an event emitted beyond the run, or a vocabulary resolution. The endpoint's `access` states which. A key is VIEWER unless a role was asked for at mint.

## Three shapes of answer

**Synchronous `flow.invoke`.** Body validated against the flow's body-bound input slots (`additionalProperties: false` — an unknown body field is a 422), query against the declared query params (an **undeclared query key is a 422**, and an **empty value is absent**: `?category=` drops an optional filter, and a required parameter sent empty is a 422), path params by the matcher. The flow runs inline under `syncTimeoutMs` (default 30 s, ceiling 120 s); the bound output is validated against the response contract and sent with the endpoint's `successStatus`. On timeout: **504, and the run stops at its next step** — no further step starts, but the step already running (an AI call, a fetch) finishes, and every paid call made stays billed. A run the timeout cut short discards what it staged: record changes, mail, published events and enqueued jobs. Writes that are never staged still stand — vector points, stored files, newly minted terms — including ones the step in flight makes after the 504. And a timeout that lands after the last step, while a finished run's writes are being committed, lets them land behind the 504. So a 504 does not prove nothing was written; retry with the same `Idempotency-Key` (Headers worth knowing, below, says what that buys).

**Asynchronous `flow.invoke`.** `202 { id, status, statusPath }`. `statusPath` is **relative** to the project host: `/v1/_invocations/{id}`, which answers `{ id, status, output?, error? }` with status `PENDING`, `PROCESSING`, `READY` or `FAILED`. `output` appears only on READY and is re-validated against the endpoint's current response contract — an edited contract turns the read into a 502. The read is owner-scoped: an unknown, foreign or another project's id is the same 404 `No such invocation.`

**Streaming `flow.stream` and `events.subscribe`.** The response is `text/event-stream`; see below.

## Server-sent events

- Frame: `event: <name>` then `data: <JSON>`. An opening `:open` comment, then `:keep-alive` every 15 seconds.
- **`flow.stream` emits `stage`, `delta`, `result`** — plus `event` when the endpoint declares `surfaceEvents`. `stage` is `{ skill, phase: start | complete }`. `delta` is `{ slot, chunk }` where `chunk` is a **monotonic growing suffix**: concatenate to reproduce the value. `result` is the bound output object. Deltas are sent only while a `text.generate` step with structured output writes the streamed field; a stream can carry none at all, so render from `result` and treat deltas as a preview.
- **`events.subscribe` emits exactly one frame name, `event`**, carrying the emitted event's envelope verbatim. It does not close when the events stop — only on the lifetime bound below, a revocation, a fall-behind or the transport failing.
- **`error`, `close` and `done` are always permitted**, and **every stream's last frame is `done`** (`data: {}`): after `result` on a `flow.stream` that finished, and after `error` or `close` on any stream. Read `done` as the end of the stream, never as success. `error` is the transport failing or a flow failure surfaced in-band — its `code` is the only signal, because the HTTP status is already 200. A refusal keeps its own code there: `FLOW_OUTPUT_MISSING`, `RECORD_NATURAL_KEY_TAKEN`, `CHANGE_SET_PRECONDITION_CONFLICT`. A step that failed is `INTERNAL`, with `details.phase` and `details.step` naming where — the frame a sync call would have answered as a 502. `FLOW_STREAM_FAILED` is what is left: a failure with no step to name. `close` is `{ reason }` with reason `lifetime`, `transport-unavailable`, `revoked`, `terminal` or `too-slow`; treat an unknown reason as `lifetime`.
- Every stream ends after ten to twelve minutes with `close { lifetime }` whatever the activity. Reconnect, with jitter. A subscriber that fell behind by 200 frames gets `close { too-slow }`.
- In a browser `EventSource`, a server `error` frame and a dropped socket both fire the handler named `error`; tell them apart by payload.
- **A `flow.stream` that ends early commits nothing it staged.** A client that disconnects, the stream's deadline, or a revoked session stops the run at its next step, and its staged writes (record changes, mail, events, jobs) are discarded, as a sync 504's are; unstaged writes (vector points, files, minted terms) still stand. One that ends after the last step, while the writes are being committed, lets them land even though the client saw an error or nothing.
- Refusals **before** the hijack are ordinary JSON: an ownership 404 on a `record`-scoped subscription, a 503 `STREAM_CAPACITY_EXCEEDED` with `Retry-After`, a 429 `PROJECT_CONCURRENCY_EXCEEDED` when the project already has its maximum of streams open, a 503 `STREAM_TEMPORARILY_UNAVAILABLE` (retry shortly) when the stream's binding cannot be established — the message bus is unreachable, say.
- A key on a `user`- or `record`-scoped subscription is a 403 naming the scope.

`{ code, message, details?, requestId }`. **Branch on `code`**; the message may change at any time. `requestId` is also the `x-request-id` response header — and on a synchronous invocation it **is the run id** for `GET /v1/runs/{runId}` on the api host.

A project that turned member wallets on adds a third for a signed-in member whose own wallet is empty, `MEMBER_WALLET_EMPTY`; `kipory-connect`'s `references/conventions.md` lists every 402 code with its remedy and `kipory-operate` has the detail. The credit gate skips GET, so an over-cap project degrades to read-only rather than dark.

## Headers worth knowing

- `Idempotency-Key` — a string of your choosing, one per logical operation; ignored, not truncated, over 255 characters. What a second call with the same key gets depends on the action, and nothing here expires:
  - **Async `flow.invoke`**: the first call's acknowledgement again — the same `id`, with its current `status` — and no second run. The match is per caller (the same signed-in user, or the same project for an API key) and on the key alone: the same key on a different endpoint or body still returns the earlier invocation.
  - **Sync `flow.invoke`**: no stored answer. The flow runs again and the response is the new run's. What the key buys is convergence: a per-user record an `record.create` step writes takes the same id as the first call's when the key, the user, the step and the data are the same, so the retry lands on that record instead of making a second one, and a charge the first call already recorded for the same step is not taken twice. A project-owned record is identified by its data alone, with or without a key. Two cases never converge: a per-user create inside a `flow.fan-out` branch (a retry writes a second record there), and a retry made after the flow was edited.
  - **`flow.stream`**: as sync; each retry attempt (`retry`) runs under its own key derived from yours, so attempt two never converges on attempt one.

  Without the header each call is its own operation: a sync call gets a fresh key per run, and an async invocation is keyed by its own `id`, which only makes the platform's own retries of that one invocation converge.

- `X-Credits-Charged` — on every billable response, 2xx, 4xx and 5xx alike: the credits this request was billed, as an integer. **One credit is one micro-USD** — `5139` is $0.005139. It is the total recorded against the request by the time the response was sent.
- `x-request-id` — the run id for a synchronous invocation and for a stream (one run, whatever its retry attempts). A client-supplied value is ignored. Such a run reads `source.kind: "request"` on `GET /v1/runs`, naming no endpoint; an async call's run reads `endpoint` with the endpoint's key.
- Rate limits are per minute, keyed per API key (with a per-key override) or per signed-in user, whether the session arrives as a cookie or a bearer. On top of those, the project as a whole has a per-minute ceiling across every key and user, and a ceiling on requests running and streams open at once. A user's `/v1/me*` and `/v1/credits*` calls have a bucket apart from the rest. A caller refused by the project's ceilings gets `details.scope: "project"`: the load comes from the whole project, so backing off this one client may not help. A response under the limit carries `x-ratelimit-remaining` and `x-ratelimit-reset` but not the limit itself, so pace on `x-ratelimit-remaining`. What a 429 carries depends on which limit refused: the caller's own per-minute limit sends all three headers and `retry-after`; the project's per-minute ceiling (`RATE_LIMITED`, `scope: "project"`) sends all three describing the project's bucket (remaining `0`) and `retry-after`; `PROJECT_CONCURRENCY_EXCEEDED` sends only `retry-after`. A request whose count the limiter's store refuses is let through. If the store goes down while the API is running, requests wait for it rather than pass unlimited; if it was already down when the API started, each API process counts on its own.

## What a signed-in user is to a flow

The `userInfo` provider slot: `{ userId }`, plus `profile` — typed by the project's connected profile schema — when one is connected ([sign-in.md](sign-in.md), The end-user profile, has the routes that connect one). The caller cannot set or spoof it. Its own profile is `/v1/me/profile` on the project host (values), and `/v1/me` is identity only. A key request carries no `userInfo` at all. How a person gets the session in the first place, how they sign out, and the rest of the `/v1/me` account routes are in [sign-in.md](sign-in.md).
