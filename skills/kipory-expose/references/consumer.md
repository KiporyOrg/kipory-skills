How a request to `<baseUrl>/v1/<your-path>` is served. This is what your product's client — or your own agent calling the product — needs to know. The design API on the api host is `kipory-connect`'s subject, not this file's.

- **`baseUrl` is the project's own origin.** Read it from `GET /v1/projects/{nodeId}` or from the project's entry in `GET /v1/grant`; an endpoint's `invokeUrl` is `baseUrl` plus its path. Do not infer either from the base URL you were handed: they follow the deployment's own configured address (`kipory-connect`'s `references/conventions.md` owns the two-hosts rule).
- **Where it is `null`** — a deployment configured on a bare `localhost`, with no host name to derive a project host from — send the same request to the api's base URL with the header `x-kipory-project-slug: <project slug>`; without it that host answers 404 `No project matched this request's host`, naming the header. That header is read on a local or development stack only; a production deployment never reads it.
- **A response is JSON, a redirect, an empty 204 or server-sent events.** No endpoint answers HTML or a file. A refusal's `code` is the platform's word for its status (`FORBIDDEN`, `GONE`…); the endpoint's own word for it is `details.reason`.

## Matching

- One catch-all serves every method under `/v1/`. A **coded route always wins** over it; among your endpoints, fewer path params wins, then more literal characters, then the endpoint key.
- Method is matched, not leaked: the right path with the wrong method is the same 404 as no path. A path over 2048 characters is a 404. Any `/v1/_…` path other than the built-in invocation status is a 404.
- The write gate runs **after** matching, so an unknown path 404s rather than revealing itself as a 403.

## Credentials

Three, resolved in this order from one hook:

1. `Authorization: Bearer <api-key>` — a machine key. Its grant must **reach** the project, else 403 `FORBIDDEN` (`Token is not valid for this API`). A key never has a user: its runs are project-owned, it gets no `userInfo`, and it is refused by any flow that reads or writes person-owned records.
2. `Authorization: Bearer <session-token>` — the opaque token a native app receives on sign-in, or an app on the project's own proven domain receives from `POST /v1/auth/handoff/exchange` (that one works on this project's host only); presented verbatim.
3. The session cookie — a browser user.

An `Authorization` header present but not `Bearer …` is an immediate 401 with no fall-through to the cookie. A session's user must still be active and a member of the project on every request; a key has no such third party.

A VIEWER principal — session or key — is refused on any call that counts as a write: 403 `FORBIDDEN`, whose message names the credential — `This API key's role (viewer) can only read …` for a key, `Your role (viewer) is read-only …` for a session. An async invoke or a DELETE always counts; any other GET never does; anything else does when the endpoint's bound flow reaches an action that changes data — a function that writes, an event emitted beyond the run, or a vocabulary resolution. The endpoint's `access` states which. A key is VIEWER unless a role was asked for at mint.

## Three shapes of answer

**Synchronous `flow.invoke`.** Body validated against the flow's body-bound input slots (`additionalProperties: false` — an unknown body field is a 422), query against the declared query params (an **undeclared query key is a 422**, and an **empty value is absent**: `?category=` drops an optional filter, and a required parameter sent empty is a 422), path params by the matcher. The flow runs inline under `syncTimeoutMs` (default 30 s, ceiling 120 s); the bound output is validated against the response contract and sent with the endpoint's `successStatus`. On timeout: **504, and the run stops at its next action** — no further action starts, but the action already running (an AI call, a fetch) finishes, and every paid call made stays billed. A run the timeout cut short discards what it staged: record changes, mail, published events and enqueued jobs. Writes that are never staged still stand — vector points, stored files, newly minted terms — including ones the action in flight makes after the 504. And a timeout that lands after the last action, while a finished run's writes are being committed, lets them land behind the 504. So a 504 does not prove nothing was written; retry with the same `Idempotency-Key` (Headers worth knowing, below, says what that buys).

**A view endpoint** (a `GET` whose flow answers one `record.view` page) is called the same way, with its query typed by the view: numbers and booleans as written in the URL, `?limit=` from 1 to the view's maximum, any other key a 422. It answers `{ items, nextCursor, prevCursor, paging: null }`: pass `nextCursor` back as `?after=` and `prevCursor` as `?before=`, with the same other params — a cursor sent with other params, by another person or to another view is `400 VIEW_CURSOR_INVALID`. When it answers an `ETag`, send it back as `If-None-Match`; `304` means nothing it reads changed, and costs no run and no credits. The project's OpenAPI document says which operations answer `304`.

**Asynchronous `flow.invoke`.** `202 { id, status, statusPath }`. `statusPath` is **relative** to the project host: `/v1/_invocations/{id}`, which answers `{ id, status, acceptedAt, startedAt, attempt, output?, code?, error?, failure?, waiting? }` with status `PENDING`, `PROCESSING`, `READY` or `FAILED`. A `FAILED` read carries `code` — the one the same call made synchronously would answer (`FLOW_FAILED`, `RECORD_NOT_FOUND`, `QUOTA_EXHAUSTED`…) — when one names the failure, and `failure`, the run's closing record. `output` appears only on READY and is re-validated against the endpoint's current response contract — an edited contract turns the read into a 502. The read is owner-scoped: an unknown, foreign or another project's id is the same 404 `No such invocation.`

**Streaming `flow.stream` and `events.subscribe`.** The response is `text/event-stream`; see below.

## Server-sent events

- Frame: `event: <name>` then `data: <JSON>`. An opening `:open` comment, then `:keep-alive` every 15 seconds.
- **`flow.stream` emits `stage`, `delta`, `result`** — plus `event` when the endpoint declares `surfaceEvents`. `stage` is `{ action, phase: start | complete }`. `delta` is `{ slot, chunk }` where `chunk` is a **monotonic growing suffix**: concatenate to reproduce the value. `result` is the bound output object. Deltas are sent only while a `text.generate` action with structured output writes the streamed field; a stream can carry none at all, so render from `result` and treat deltas as a preview.
- **`events.subscribe` emits exactly one frame name, `event`**, carrying the emitted event's envelope verbatim. It does not close when the events stop — only on the lifetime bound below, a revocation, a fall-behind or the transport failing.
- **`error`, `close` and `done` are always permitted**, and **every stream's last frame is `done`** (`data: {}`): after `result` on a `flow.stream` that finished, and after `error` or `close` on any stream. Read `done` as the end of the stream, never as success. `error` is the transport failing or a flow failure surfaced in-band — its `code` is the only signal, because the HTTP status is already 200. A refusal keeps its own code there: `FLOW_OUTPUT_MISSING`, `RECORD_NATURAL_KEY_TAKEN`, `CHANGE_SET_PRECONDITION_CONFLICT`. An action that failed, a limit of one run, or an output that fails the response contract is `FLOW_FAILED`, with the details a sync call's 502 carries; a spent quota is `QUOTA_EXHAUSTED` and a by-id read that found nothing `RECORD_NOT_FOUND`, as a sync call answers them. `FLOW_STREAM_FAILED` is what is left: a failure with no action to name. `close` is `{ reason }` with reason `lifetime`, `transport-unavailable`, `revoked`, `terminal` or `too-slow`; treat an unknown reason as `lifetime`.
- Every stream ends after ten to twelve minutes with `close { lifetime }` whatever the activity. Reconnect, with jitter. A subscriber that fell behind by 200 frames gets `close { too-slow }`.
- In a browser `EventSource`, a server `error` frame and a dropped socket both fire the handler named `error`; tell them apart by payload.
- **A `flow.stream` that ends early commits nothing it staged.** A client that disconnects, the stream's deadline, or a revoked session stops the run at its next action, and its staged writes (record changes, mail, events, jobs) are discarded, as a sync 504's are; unstaged writes (vector points, files, minted terms) still stand. One that ends after the last action, while the writes are being committed, lets them land even though the client saw an error or nothing. A model or vendor call already running when the stream is stopped is not undone: it is charged, and its answer is saved, so the same request asked again soon pays compute only; the stopped action's failure says whether its call had started. A run stopped because its caller went away closes `run-aborted` with `reason: "client-disconnect"`; a revoked session closes `cancelled`. A `deadline` names its clock in `closing.failure.deadline` — `sync-wait` (a sync endpoint's `syncTimeoutMs`), `stream-lifetime` (the stream's own time limit), `preview-clock` or `suite-budget` (preview and eval runs only) — with its `limitMs`; `closing.failure.runningActions` lists the actions it cut short and `closing.durationMs` how long the run had run. A `deadline` with no clock named is a stream the server ended. An asynchronous call's status line names the failed action and its code (`The flow failed at action "search": timeout.`, with no code when it is `error`); its `failure` carries the same. Action keys are visible to the callers of your endpoints, there and in `runningActions`: name them as you would an API field.
- Refusals **before** the hijack are ordinary JSON: an ownership 404 on a `record`-scoped subscription, a 503 `STREAM_CAPACITY_EXCEEDED` with `Retry-After`, a 429 `PROJECT_CONCURRENCY_EXCEEDED` when the project already has its maximum of streams open, a 503 `STREAM_TEMPORARILY_UNAVAILABLE` (retry shortly) when the stream's binding cannot be established — the message bus is unreachable, say.
- A key on a `user`- or `record`-scoped subscription is a 403 naming the scope.

## Headers worth knowing

- `Idempotency-Key` — a string of your choosing, one per logical operation, of at most 255 characters: a longer one is refused with 422 `IDEMPOTENCY_KEY_TOO_LONG`. A key names one request. Sent again within a day with a different method, path or body, it is refused with 422 `IDEMPOTENCY_KEY_REUSED` — unless its first request was refused before anything ran (a 422 for its body, a 402), which leaves the key unused. What a second call with the same key and the same request gets depends on the target:
  - **Async `flow.invoke`**: the first call's acknowledgement again — the same `id`, with its current `status` — and no second run. The match is per caller (the same signed-in user, or the same project for an API key) and on the key together with the request: the same key on a different endpoint or body is refused within a day, and after that starts an invocation of its own. It holds while the run's history is kept — 90 days unless the deployment's operator changed it; after that the invocation reads 404 and the same key starts a new run.
  - **Sync `flow.invoke`**: no stored answer. The flow runs again and the response is the new run's. What the key buys is convergence: a per-user record an `record.create` action writes takes the same id as the first call's when the key, the user, the action and the data are the same, so the retry lands on that record instead of making a second one, and a charge the first call already recorded for the same action is not taken twice. A project-owned record is identified by its data alone, with or without a key. Two cases never converge: a per-user create inside a `flow.fan-out` branch (a retry writes a second record there), and a retry made after the flow was edited.
  - **`flow.stream`**: as sync; each retry attempt (`retry`) runs under its own key derived from yours, so attempt two never converges on attempt one.

  Without the header each call is its own operation: a sync call gets a fresh key per run, and an async invocation is keyed by its own `id`, which only makes the platform's own retries of that one invocation converge.

- `X-Credits-Charged` — on every billable response, 2xx, 4xx and 5xx alike: the credits this request was billed, as an integer. **One credit is one micro-USD** — `5139` is $0.005139. It is the total recorded against the request by the time the response was sent.
- `x-request-id` — the run id for a synchronous invocation and for a stream (one run, whatever its retry attempts). A client-supplied value is ignored. Such a run reads `source.kind: "request"` on `GET /v1/runs`, naming no endpoint; an async call's run reads `endpoint` with the endpoint's key.
- Rate limits are per minute, keyed per API key (with a per-key override) or per signed-in user, whether the session arrives as a cookie or a bearer. On top of those, the project as a whole has a per-minute ceiling across every key and user, and a ceiling on requests running and streams open at once. A user's `/v1/me*` and `/v1/credits*` calls have a bucket apart from the rest. A caller refused by the project's ceilings gets `details.scope: "project"`: the load comes from the whole project, so backing off this one client may not help. A response under the limit carries `x-ratelimit-limit`, `x-ratelimit-remaining` and `x-ratelimit-reset`, so pace on `x-ratelimit-remaining`. What a 429 carries depends on which limit refused: the caller's own per-minute limit sends all three headers and `retry-after`; the project's per-minute ceiling (`RATE_LIMITED`, `scope: "project"`) sends all three describing the project's bucket (remaining `0`) and `retry-after`; `PROJECT_CONCURRENCY_EXCEEDED` sends only `retry-after`. A request whose count the limiter's store refuses is let through. If the store goes down while the API is running, requests wait for it rather than pass unlimited; if it was already down when the API started, each API process counts on its own.

## What a signed-in user is to a flow

The `userInfo` provider slot: `{ userId }`, plus `profile` — typed by the project's connected profile schema — when one is connected ([sign-in.md](sign-in.md), The end-user profile, has the routes that connect one). The caller cannot set or spoof it. Its own profile is `/v1/me/profile` on the project host (values), and `/v1/me` is identity only. A key request carries no `userInfo` at all. How a person gets the session in the first place, how they sign out, and the rest of the `/v1/me` account routes are in [sign-in.md](sign-in.md).
