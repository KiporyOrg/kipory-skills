# An embedding's fields, and activation

Read this when you state an embedding, change its model or chunking, or activate a generation — step 1 of `SKILL.md`'s order, in full. In the project document an embedding is a row of `project.ai.embeddings` — `{ model, matchExactWords, chunking, label? }`; the row API (`/v1/embeddings`) spells the same fields the same way.

- **`model`** is an embedding model's id from `GET /v1/ai-models?type=embedding` — nothing else lists them. A listed model is not a working one: before you choose, read `GET /v1/ai-calls?project={nodeId}&origins=all&outcome=error` for recent rows with `errorCode: "quota-exhausted"` by provider and pick another provider's model if its account is out. On a project with no history the first failed embed is the probe — see the indexing failure below.
- **`matchExactWords`** is required: `true` also indexes each record's exact words, so a `semantic` clause weighs a literal match beside meaning (names, codes); `false` is meaning alone, and finds a query worded differently from its record better. Turn it on when people search by exact words — names, codes, ids. It is fixed for a generation. You name no vector anywhere: a `search` use names fields only, each `search` field is indexed on its own, and a `semantic` clause picks one by `field`. The embedding read's `searchFieldsPerTable` is how many fields of one table may be marked `search` (4 on every embedding); one more is refused `USES_SEARCH_FIELDS_OVER_LIMIT`.
- **`chunking`** is exactly one of two forms: `whole` (one point per record) or `{ tokens: 400, overlap: 50 }` (token-sized pieces, `overlap` strictly below `tokens`). Any other value is a 422. A table's `uses.search.chunking` takes the same two forms.
- **`project.ai.defaultEmbedding`** names the embedding a `search` use gets when it names none; left out of a new project, it is the one keyed `default`, and `ai` stated without it keeps the pointer. `default` always resolves: naming it, or naming none, where it does not exist creates it (the inherited embedding model, `matchExactWords: false`, `chunking: whole`). The export prints that row, and a table's `embedding` line, only once they differ from the engine's default; stating them as it changes nothing in a plan.
- **A stated embedding row is whole**: `model`, `matchExactWords` and `chunking`, even for `default`. A plan that gets only some refuses the row with a fix that fills the rest from what the key holds now; to change `chunking` alone, `PATCH /v1/embeddings/{id}` instead, and `matchExactWords` or `model` with a new generation.

**Read them all in one call:** `GET /v1/projects/{nodeId}/settings` answers `embeddings` (null when it could not be read this time): `engineDefault`, what the engine would create now as `default` (`model`, `matchExactWords`, `chunking`; null when no embedding model resolves); `defaultKey`, the project's default (null until a table first searches); and every embedding, each with its active generation's `id` and `version`, `isDefault`, `isEngineDefault`, the `tables` that search with it (a table stays on its embedding until told otherwise) and `deleteRefusal`. `source` is `platform-default` while the project has none of its own, or its default is exactly the engine's.

Activation is direction-agnostic — pointing at a superseded generation is the rollback, and it is a second reindex: records that already moved are embedded and billed again. Its response names `movedTables` and `touched`. An empty `movedTables` means it was already active; repeating is safe.
