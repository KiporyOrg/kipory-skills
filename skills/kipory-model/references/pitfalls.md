# What will bite you — modelling a project's data

Read this before you build on a table, relation, vocabulary or embedding profile: each bullet is a trap, what happens, and what to do about it.

- **Working around a problem in silence.** When something on Kipory stops you — an unexpected error, a doc that said something untrue, a capability you need that is missing — file a report: `kipory-connect`, "When something stops you".
- **Linked records come with the read; a walk of any depth does not exist.** `GET /v1/records/{id}/links/{relationKey}` walks one hop, one relation, and takes no depth. To bring each record's linked records — the author of each book, and the author's publisher — set `linked` on a flow's `record.read`, `record.list` or `record.query`, or in the body of `POST /v1/records/query`: two levels, one step. A query still selects by a condition one link away only (`peer`). `references/packs/relations-and-links.md`, "Linked records in one read", has the linked read, when it answers one record or a list, and its limits.
- **An empty traversal is not proof of no links.** A relation the project does not have answers 200 with an empty list, never 404 (`kipory-data` walks links). Check the relation exists before concluding a write went missing.
- **A `link` field does not check that its target exists.** A field naming a record that does not exist, is in another project, or is the record itself saves without an error and produces no link. Read the link back (`GET /v1/records/{id}/links/{relationKey}`) when it matters.
- **A term filter finds active terms only.** A vocabulary with `mint: candidate` files records under candidate terms, which a record read shows — but `term=` on the records list and a query's `term` clause do not match them until the term is admitted (`PATCH /v1/terms/{id}`).
- **Re-classifying a record replaces on a `one` vocabulary.** `term.upsert` swaps the record's term there (and drops its terms nested under the old one); on a `many` vocabulary it adds. Two terms for one record in one run are refused — `references/classification-runtime.md`.
- **Do not give a vocabulary the key of a field of a table that surfaces it.** A list row carries each vocabulary as a top-level field named by its key, so vocabulary `cuisine` beside submitted field `cuisine` would replace the value with the term. The table save refuses the pair with `USES_VOCABULARY_SHADOWS_FIELD`, and a type edit that adds the field later with `TYPE_UNSAFE_FOR_TABLE`; a pair made any other way (a flow output of that name) saves and shows only in the table's diagnostics. Name the vocabulary differently (`cuisineTag`). <!-- field-ok: cuisineTag — an example vocabulary key a project would author, not a platform field -->
- **A 404 on a row route means the id is not one you can see.** A design route that addresses a row (`/v1/terms/{id}/merge`, `/v1/vocabularies/{id}`, …) answers a missing id and one in a project your key does not reach with the same `404 NOT_FOUND`, so ids cannot be probed; re-read the id from its list. A 403 `insufficient_project_role` there is a real role gap on a row you can see, and `details.requiredRole` names the floor.
- **On a vocabulary patch, `version` is required**, an omitted field preserves, and an explicit null clears only some fields: the proposal, the resolver binding and its params. On `matching` and the mint policy a null is a **no-op**, because those columns are never empty.
- **A schema edit cascades.** Read the tables pack on what a type change reaches before editing one that tables already reference.
- **A field is a date only when its type says so.** `{type: string, format: date}` (or `date-time`) makes it one, which `lt`/`lte`/`gt`/`gte` filters need, with a full ISO time as the value (`2026-11-09T00:00:00Z`; a fixed date-only value is refused at save); a bare string of `YYYY-MM-DD` compares by `eq` only. Decide before records exist: changing a field's format later is a type change (`kipory-evolve`).
- **Rename a field; never remove and re-add it.** `renameFields` on the type keeps every value, moves every reference the platform can place, and lists the expressions and templates you must settle yourself. Removing the field instead is refused while records hold it, and dropping and re-adding loses the values. It needs ADMIN, and it breaks callers that read the old name — the plan's `renames[].exposures` lists them (tables pack, renaming a field).
- **`expand=embedding` and `expand=vectorProgress` are refused on the tables list.** They are per-row scans; ask them on `GET /v1/tables/{id}`. On tables, `expand` is **comma-separated** (`?expand=embedding,vectorProgress`); repeating the parameter is a 422 `Expected string, received array`.
- **An indexing failure is silent on the record and the table.** Records stay `indexState: "never"` and `vectorProgress.remaining` stops falling; neither says why. The cause is in the AI-call list: `GET /v1/ai-calls?project={nodeId}&origins=projection` — each failed embed is a row with `errorCode` (`quota-exhausted`, …); read one by id (`GET /v1/ai-calls/{id}`) for the provider's `errorMessage`. A failed embed is retried three times within about fifteen seconds, then only by the daily re-index sweep (08:00 UTC). The usual remedy is a new profile generation on another embedding model, then activate it.
- **Readiness is the diagnostic here.** Re-read the vocabulary or relation with `expand=readiness` (a relation also with `liveLinkCount`, or `unproven` never shows): `blocked` cannot work (`RESOLVER_UNBOUND` on an unbound semantic vocabulary), `inert` is wired to nothing, `unproven` has never resolved — no run has filed one of its terms onto a record and applied (a preview does not count) — expected an hour after authoring, a question a year later.
- **An embedding profile carries two numbers.** `generation` numbers the model-and-`keywords` pair its index was built with, minted by `POST …/generations`, never sent back. `version` is its lock, like every other row's: required on the PATCH and on `POST …/activate`, and a stale one is 409 `VERSION_CONFLICT`. Changing the model or `keywords` goes through a new generation and re-embeds everything; changing `defaultChunking` re-derives and re-embeds every table that inherits it, without a new generation.
- **`uses` is sent whole.** A PATCH carrying it replaces the statement; reordering two `filter` fields moves their storage slots and re-stamps every record of the table. Read it, change it, send it back with the `version` you read — and ask the same PATCH with `validateOnly: true` first if you are not sure what it derives to.
- **A 2xx is not a promise it will run** — see `kipory-connect`'s conventions. Runtime is stricter than authoring.
