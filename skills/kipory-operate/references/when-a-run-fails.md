# When a run fails — being told, health and pausing, whose failure, `partial`

Read this to be told when an unattended run fails, or to learn why a schedule or trigger was paused: the routes, then bullets that each say what the platform does and what to do.

## The routes

```
GET  /v1/failed-runs?project={nodeId}      the runs whose latest close is `failed` or `partial`, newest first (cursor-paged)
GET  /v1/failed-runs/summary?project={nodeId}&from=…   the same runs grouped by flow, class and code, the commonest first
GET  /v1/projects/{nodeId}/alerts          every schedule, trigger, table or endpoint that is failing, quiet, about to be paused or paused
GET  /v1/projects/{nodeId}/alerts?include=required-gaps   also the stored records that lack a field their type requires, counted by table and field
POST /v1/platform-events/test              { project, type, subject?: { kind, key } } — record one example event and fire the triggers on it
```

An **unattended run** is a schedule's occurrence, a trigger's fire, an asynchronous endpoint call or a record's processing: nobody is waiting on the answer. `references/packs/triggers.md` ("Being told when a run fails") and `references/packs/schedules.md` ("health, and being paused") have the detail; `references/api/failures.md` the fields.

## What the platform does

**Being told**

- **A failed run cannot report itself.** It keeps nothing it wrote, and an `event.emit` it reached is never recorded, so no step of a flow can announce that flow's own failure. The platform records the failure for it, as an event in the project's `platform` category.
- **Seventeen `platform` event types, and they are the platform's.** `run.failed`, `run.failures`, `run.partial`, `health.failing`, `health.recovered`, `health.quiet`, `health.pause-warned`, `health.paused`, `mail.failed`: one message a run sent was refused, failed or bounced, `price.changed`: a model the project follows moved, or a price it paid this week changed, with the day's cost before and after, `member.left`: a person's seat in the project ended — they left, were removed, or deleted their account, and `flow-health.failing` / `flow-health.recovered`: a flow's health gained errors where it had none — after an edit or after a new build whose rules judge it differently, though its runs may still succeed — or has none again, and `vendor.unavailable` / `vendor.available`: a service the platform provides stopped serving, or serves again — once each per outage, to each project whose flows hold a step that can run only on that platform account, naming the `vendor` and the `functions` your flows use on it (model providers are not covered yet), `vendor.changed`: Kipory changed which vendor serves a function your enabled steps use, what a result of it costs, or who processes its data — once per change, naming the function and the vendor and credits per result before and after, and `notice.published`: Kipory announced a breaking change that reaches the project — its notice's id, title and date, the notice itself read with `GET /v1/notices/{id}?project=`. Every project has them; you cannot add to the category, change it or emit into it, and a project document neither creates nor prunes them.
- **The failure trigger is an ordinary trigger on one of them, bound to an ordinary flow**: `POST /v1/triggers` with `categoryKey: "platform"`, `eventKey: "run.failed"` and a flow that posts to your chat (`url.send`), mails someone (`email.send`) or writes a record. The flow reads `event.data`: the run (`id`, `kind`, `flowKey`, `attempts`), its `subject` (`{ kind, key }`, `kind` one of `schedule`, `trigger`, `endpoint`, `table`), `closing.failure` (class, owner, the failing step, a `code` and the platform's sentence for it; when no step failed, the `cause` that closed the run and, for a save that was refused, the `refusedWrite`) and the subject's `health`. Ids, keys, codes and counts only — never an input or a step's value; read those from the run.
- **Listen to `run.failures` as well.** Only the first final failure of a subject is a `run.failed`. Later ones are folded into `run.failures` summaries — the first a minute later, then at doubling intervals up to an hour — each with a `count`, a count per class and `failedRunsPath`, the failed-runs list filtered to exactly what it counted. Five thousand records failing in ten minutes are five events.
- **Nothing is recorded** for an attempt the platform is about to start again, a run a person cancelled, a preview, or a synchronous call, whose caller already has the answer.
- **A failure trigger's flow is never handed its own failure.** A run started by a platform event, and everything that run starts, causes no platform event when it fails. A broken failure flow fails once per event and stops; its trigger reads `failing`, and the alerts read marks it `failureTrigger: true`. Such a trigger defaults to `overlapPolicy: "allow"`, is never paused, and runs in a slot of its own.
- **Prove the failure trigger before something fails.** `POST /v1/platform-events/test` records one event of the type, with example `data` carrying `test: true`, for a subject the project has: a schedule, trigger, table or endpoint for `run.*` and `health.*`, a flow (`kind: "flow"`) for `flow-health.*`, and none for `mail.failed`, `price.changed`, `member.left` and `vendor.*`. Every enabled trigger on the type fires, and the flows they start are ordinary, charged runs. The answer says how many triggers listen: zero means nothing ran.
- ⚠️ **Nothing is mailed.** The platform sends no mail about a failing, quiet, warned, paused or recovered schedule, trigger, table or endpoint. A project that wires no trigger on a `platform` event is told nothing, and nothing of its is ever paused. It learns only what it asks for: `health` on each schedule, trigger, table and endpoint read, the alerts read, the failed-runs list, and `lastRunStatus`. A document plan of a project that runs schedules or triggers with no enabled trigger on `platform/run.failed` says so as `DOCUMENT_NO_FAILURE_LISTENER` — information, blocking nothing.

**Health, and being paused**

- **Every schedule and trigger read carries `health`**, one word in `state`: `healthy`, `failing` (with `failingSince` and `countedFailures`), `quiet` (a schedule whose occurrence should have run and has not, for five intervals and at least an hour), `warned` (it will be paused at `pauseAt`) or `paused`. A table and an endpoint carry `healthy` or `failing` and are never paused; an endpoint counts its asynchronous calls only.
- **Only the subject's own failures count** — class `logic`, `definition` or `vendor`. A run the platform failed, a spend cap or a cancelled run never moves `health`. One run that succeeds ends the failing spell.
- **The pause rule.** A schedule is due to be paused when it has been failing for the longer of 48 hours and five of its own intervals, with at least five counted failures — or when at least 95% of at least 20 runs in seven days failed. For a trigger the time is 48 hours. The platform then records `health.pause-warned`, and pauses it 24 hours later if it is still failing.
- ⚠️ **Pausing needs a listener.** In a project with no enabled trigger on `platform` / `health.pause-warned`, nothing is ever paused and each row reads `health.pauseArmed: false`. A row that must never be paused states `failurePolicy: "keep-running"` on create or PATCH (the default is `"pause"`).
- **Paused is a state of its own, beside `enabled`.** The read shows `pausedAt` and `pauseReason` (`failing` or `mostly-failing`). Nothing fires, and no occurrence or decision is recorded; a paused trigger's events are not replayed when it resumes. `enabled: true` does not clear it, and neither does a project document — only `POST /v1/schedules/{id}/resume` or `POST /v1/triggers/{id}/resume`. `GET /v1/bootstrap` leaves `health`, `pausedAt` and `pauseReason` out: read the row, or the alerts read.

**Whose failure it is**

- **A failed run's closing record names a `class` and an `owner`** — `failure` on a schedule's or trigger's run, `closing.failure` on `GET /v1/runs` and each row of the failed-runs list.

  `logic`: your flow's own expression, input or data rule refused. `definition`: the flow cannot be run as it is stored. `limit`: a spend cap, the paying account's standing or an allowance. `vendor`: a site or service the flow called. `platform-busy`, `platform-interrupted`, `platform-fault`: the platform's own — no worker was free, the worker stopped, or the platform itself (its engine, database, queue or worker) failed. `platform-account`: one of the platform's own accounts at a vendor or model provider could not serve the call — out of credit, its key refused, or throttled; it moves no `health`. `cancelled`: it was stopped on purpose.

  `owner` says who has to act: `customer` (you), `vendor`, `platform` (nothing in your flow needs changing) or `caller`. `retryable` says whether running it again, unchanged, could end differently.

- **Waiting for a worker is not a failure.** A queued step's time limit counts the time its job runs, not the wait for a free worker. Only a job no worker takes for five minutes fails its step — class `platform-busy`, no compute charged — and that is one of the failures the platform runs again.
- **The platform runs its own failures again.** When an attempt of an unattended run closes `platform-busy`, `platform-interrupted`, `platform-fault`, or `platform-account` from a throttled account (`rate-limited`), the run is not failed: it keeps its run id, its `status` goes back to `pending`, and `waiting { reason, attempt, notBefore }` says why and when the next attempt may start. At most three attempts <!-- count: run-attempts -->; only the last attempt's failure is the run's. A failure of your flow, of a vendor or of a limit is never run again, and neither is a synchronous call. A platform account out of credit or with its key refused (`platform-account`, `retryable: false`) is not run again either: the run fails at once, since topping the account up takes an operator, not seconds.
- ⚠️ **What a run started again repeats, and charges.** It runs its steps again from the start. Nothing the failed attempt staged was saved, so no record is written twice. A step's compute is charged once per run however often it is repeated; a model or vendor call that is really made again is charged again, and one a cache answers is not. The worst case is three attempts <!-- count: run-attempts -->: a paid call can be charged three times <!-- count: run-attempts -->. `repeatedByPlatform` on `GET /v1/runs/{runId}/spend` says how much of a run's cost came from this (`references/spend.md`).
- **A run started again runs the flow it first started with.** A flow edit saved between two attempts is not taken by a run already under way — neither in its own flow nor in a sub-flow that flow calls by a fixed reference; the next run takes it. Not held back: a sub-flow chosen at run time and first reached on a later attempt, types, model bindings, vocabularies and secrets — a later attempt reads those as they are then.
- **A deployment of the platform lets runs finish.** A worker that is being replaced takes no new run and lets the ones it holds finish, for up to five minutes. A run still going after that is interrupted (`platform-interrupted`) and started again as above. ⚠️ Meanwhile no record's processing and no asynchronous run — an endpoint call, a schedule's occurrence, a trigger's fire — is picked up for up to six minutes: they wait in the queue and are not failed.

**`partial`, and the list**

- **A run that carried on past a failure closes `partial`**, a third result beside `succeeded` and `failed`: a step or a sub-flow call that failed where a `try` caught it, a step a `repeat` stopped at, or an `each` whose `maxFailedBranches` or `maxFailedShare` allowed some of its elements to fail, and some did (`kipory-build`'s `references/patterns.md` and `fan-out.md`). A failure a `try` caught is still a failure the run carried past: it never closes `succeeded`. Its changes are applied — the failed elements' own are dropped — and its invocation reads finished; `closing.verdict` is `partial` and `closing.absorbed { steps, calls, branches, owner }` counts what it carried on past, `owner` saying whose those failures mostly were (`customer`, `vendor`, `platform`, `caller`). A schedule's or trigger's `status` and `lastRunStatus` read `partial`, and the project is told in `platform/run.partial` summaries.
- **`GET /v1/failed-runs?project={nodeId}` is the list a summary points at**: unattended runs whose latest close is `failed` or `partial`, newest first. Filter by `subjectKind` with `subjectKey`, by `class`, by `verdict`, and by when the run closed (`from`, and `to`, which is exclusive); walk `after=<nextCursor>`. A run the platform is about to start again is not on it, nor is a cancelled one. It keeps a run for a limited time, and a `partial` occurrence old enough to have left it reads `succeeded`.
